# ADR-0014: ประชากรรายตำบลและรายหมู่บ้านมาจากไฟล์ `stat_m` ไฟล์เดียว แทน `stat_t`

- สถานะ: ยอมรับ · 11 พ.ย. 2569 (D13) · แก้ข้อ "ต่อปีใช้สองไฟล์" ของ ADR-0011
- เกี่ยวข้อง: SPEC §2.3, §2.6, §6, §9.2, §12.1, D13, SCHEMA §2.6–2.8, §3.8–3.9, §7, §9, §11, GLOSSARY "หมู่บ้าน", "ไม่ระบุหมู่", ADR-0011

## บริบท

แผงตำบลบนหน้าแรกแสดงประชากรทะเบียนราษฎรของทั้งตำบล ผู้ใช้ต้องการเห็นแยกรายหมู่บ้าน stat.bora มีไฟล์รายปีระดับหมู่บ้าน `stat_m{yy}.txt` ข้อมูลที่ตรวจเมื่อ 11 พ.ย. 2569:

- `stat_m` มี 13 ค่าต่อบรรทัด เหมือน `stat_t` ทุกช่อง และเพิ่มบรรทัดหมู่บ้าน (`CCAATTMM-CODE` ≠ `0`) ไฟล์ทั้งประเทศมีราว 92,400 บรรทัด ขนาด 18 MB เทียบกับ `stat_t` ที่มี 2 MB
- เมื่อตัดบรรทัดหมู่บ้านออก `stat_m` ตรงกับ `stat_t` ทุกบรรทัดทั้งไฟล์ ตรวจกับปี 2564 และ 2568 และไฟล์ปี 2568 ทั้งสองแก้ไขล่าสุดเวลาเดียวกัน (24 มี.ค. 2569)
- อำเภอสองมี 85 หมู่บ้านใน 8 ตำบล ชุดรหัสและชื่อเหมือนกันทุกปีตั้งแต่ 2564 ถึง 2568 · แต่ละปีมี 94 บรรทัดหมู่บ้าน เพราะหมู่บ้านในเขตเทศบาลตำบลสองบางหมู่มีบรรทัดทั้งใต้สำนักทะเบียน `5406` และ `5489` · ภายในแต่ละสำนักทะเบียน ผลรวมบรรทัดหมู่บ้านเท่ากับบรรทัดตำบล
- มีบรรทัดที่รหัสหมู่บ้านลงท้าย `00` คือคนและบ้านในตำบลที่ไม่ได้นับไว้ในหมู่ใด (ไม่ระบุหมู่) อำเภอสองมีแค่ที่บ้านกลาง (14 คน 3 บ้าน ในปี 2568) ส่วนทั้งประเทศมี 2,016 บรรทัด

## การตัดสินใจ

- ต่อปีใช้ `stat_m{yy}.txt` แทน `stat_t{yy}.txt` คู่กับไฟล์อายุเดิม ผู้ดูแลจึงยังอัปโหลดปีละ 2 ไฟล์ หน้า `/sync` ไม่รับ `stat_t` แล้ว
- จาก `stat_m` เบราว์เซอร์ส่งแถวตำบลไปชีต `registry_population` ตามเดิม และส่งแถวหมู่บ้านไปชีตใหม่ `registry_population_village` ที่มีคอลัมน์ตรงกับไฟล์ ชีตและสัญญาเดิมไม่เปลี่ยน GAS ตรวจว่าผลรวมหมู่บ้านต่อ (สำนักทะเบียน, ตำบล) เท่ากับแถวของ `registry_population` ในปีเดียวกัน
- หนึ่งหมู่บ้านคือหนึ่งรหัส 8 หลัก รวมยอดข้ามสำนักทะเบียนแบบเดียวกับที่รวมตำบล ชื่อแสดงคู่กับหมู่ที่ เพราะชื่อซ้ำกันในตำบลเดียวได้ · บรรทัดไม่ระบุหมู่แสดงเป็นแถวสุดท้าย และไม่นับเป็นหมู่บ้าน
- หน้าแรกแสดงหมู่บ้านเฉพาะปีที่แสดง ในแผงตำบล ต่อจากหน่วยบริการ · `population.json` มีแถวหมู่บ้านเฉพาะปีนั้น แบบเดียวกับแถวอายุ
- อัปโหลดย้อนหลัง 2564–2568 ใหม่ด้วย `stat_m`

## ทางเลือกที่ไม่เลือก

- เพิ่ม `stat_m` เป็นไฟล์ชนิดที่สาม คงไว้คู่กับ `stat_t`: ผู้ดูแลต้องอัปโหลดปีละ 3 ไฟล์ และต้องมีโค้ดตรวจว่าแถวตำบลของสองไฟล์ตรงกัน ทั้งที่ทั้งสองไฟล์มาจากข้อมูลชุดเดียวกัน
- รับได้ทั้ง `stat_t` และ `stat_m`: ต้องดูแลโค้ดตรวจและส่งสองทาง เพื่อรองรับปีที่ไม่มีหมู่บ้าน ซึ่งไม่มีใครต้องการ
- เก็บแถวหมู่บ้านในชีต `registry_population` เดิม: ต้องแก้ key ของชีต กติกาตรวจของ GAS หลายข้อ และการกรองตอน build ซึ่งกระทบส่วนที่ใช้งานอยู่แล้ว
- เก็บแถวหมู่บ้านทุกปีใน `population.json`: ไฟล์จะเกินเป้า 100 KB ของ SPEC §6.1 ทั้งที่หน้าเว็บใช้แค่ปีล่าสุด

## ผลที่ตามมา

- ผู้ดูแลเลือกไฟล์ 18 MB แทน 2 MB เบราว์เซอร์อ่านได้ และส่งไป GAS แค่ราว 100 แถวต่อปี
- ต้อง deploy GAS ที่มีชีตใหม่ก่อน merge หน้าเว็บที่ prebuild อ่านแถวหมู่บ้าน เพราะ prebuild ยังเข้มงวดกับรูปของคำตอบเท่าเดิม
- ปีที่ยังไม่ได้อัปโหลดใหม่ด้วย `stat_m` ไม่มีแถวหมู่บ้าน ถ้าปีที่แสดงเป็นแบบนั้น หน้าแรกซ่อนเฉพาะรายการหมู่บ้าน
